# 修复：新顶置的条目现在排在最前面

## 你报的问题

> 记录窗格条目置顶逻辑现在有点问题，新条目置顶后会排在所有已置顶条目最后，
> 这不符合使用习惯和直觉。请把条目置顶逻辑改成放至顶端。

## 这是我的回归，而且我在注释里把它论证成了"正确"

上一版（v1.2.4）里我**主动**把它改成了"排最后"，理由是：

* 原来的 `on_pin` 用 `insert(0, ...)`（新的排最前）
* 而启动时读的是 `ORDER BY id`，也就是**首次访问的先后**
* 两者不一致 ⇒ **用户刚顶置的那条，重启后会跳回原来的位置**

这个观察是对的。**但我选错了修法**：为了让"不需要数据迁移"这个目标成立，
我把 `on_pin` 改成 `append`，让内存顺序与 `ORDER BY id` 一致。

**我治好了"重启漂移"，代价是弄坏了你看得见的行为。** 而且我在
`on_pin` 的注释里写了很长一段论证"这样两处本来就是同一个顺序"——
**那段注释让它看起来像是想清楚了，其实只是把妥协包装成了设计。**

## 根子：一直没有"顶置顺序"这个东西

`id` 是"**首次访问**的先后"，它与"**顶置**的先后"是**两件不相干的事**。
拿 `id` 当顶置顺序，就只能在两个要求里二选一：

| | 新顶置排哪 | 重启后顺序 |
|---|---|---|
| 原来的 `insert(0)` | 最前 ✅ | **会变** ❌ |
| v1.2.4 的 `append` | **最后** ❌ | 不变 ✅ |
| **v1.2.5** | **最前** ✅ | **不变** ✅ |

## 修法：把顺序真的存下来

`paths` 表新增一列 `pin_order`（**越大越靠前**）：

* **顶置** → `pin_order` 取当前最大值 +1 ⇒ 排最前
* **取消顶置** → 归 0（**不重排其他项**，所以反复顶置/取消不会让顺序漂移）
* **读取** → `ORDER BY pin_order DESC`

内存里的 `pinned_paths` 用 `insert(0, ...)`，与库里的含义一致。
**顺序只保存在一个地方**，内存那份是它的映像。

## 老数据怎么办（**升级不会重排你的顶置列表**）

`CREATE TABLE IF NOT EXISTS` 对**已经建好的**表什么都不做，
所以老用户的库不会自动多出这一列——不迁移的话，一升级程序就会因为
`no such column: pin_order` 起不来。

迁移做的事：按**你当前看到的顺序**（也就是旧的 `ORDER BY id`）
依次回填 1、2、3……，配合新的 `ORDER BY pin_order DESC`，
**升级前后看到的顺序完全一样**。之后新顶置的才会跑到最前。

整段迁移在一个事务里：要么都成，要么都不动。
半途失败留下"有列但没回填"的状态会让顺序变乱，所以这一步不能将就。

## 验证

新增 3 项界面检查（走真实入口：选中行 → 调 `on_pin` → **读列表第一行**）：

* 最后顶置的那条排在列表第一行
* 顶置组整体顺序 = 最近顶置的在最前
* **阳性对照**：重开数据库后顺序不变（不是只在内存里对）

以及 3 条单元测试，其中一条**手工造一个旧 schema 的库**来验迁移——
用当前代码建的库已经有那一列了，测不出迁移。
**三条都被证明过"对旧实现会失败"。**

界面检查 **158 项全部通过**，单元测试 **192 条全部通过**。
