# File Tracker v1.2.1

补丁版本。修一个**发布流程本身的缺陷**，以及一处弹窗文案不一致。

## 修复

### 产物无法自报"是哪个提交构建的"（v1.2.0 的实际缺陷）

v1.2.0 的产物执行 `--version` 得到的是：

```
File Tracker 1.2.0+unknown
```

而构建是全绿的。两个缺陷叠加：

- **`_build_info.py` 生成在了错误的目录。** 打包脚本把它写在仓库根，
  于是它是一个**顶层模块** `_build_info`；而 `core.build_revision()`
  读的是 `from ._build_info import ...` —— **包内相对导入**。
  路径对不上，`ImportError` 被吞掉，永远回落到 `"unknown"`。
  现在写进 `src/file_tracker/`（包内）。

- **自检是假阳性。** 构建脚本把 `FILE_TRACKER_BUILD_REV` 设进了
  自己的进程环境，而那是 `build_revision()` 的**第 2 号来源**。
  自检时跑产物，产物从环境变量读到了哈希 ——
  **即使包里根本没写进去，校验也会通过**。
  现在自检前会把这个变量从环境里摘掉，测的是产物**自己**能不能说清楚。

> 这一条不是形式主义：v1.1.0 那个标签指向的是一条 README 提交，
> 而真正的代码提交是另一条。用户报障时，从版本号判断不出他装的是哪一个。

### 弹窗标题残留 `⚠️`

验证脚本里有一个为了贴近真实而构造的探针弹窗，标题写成了
`⚠️路径不存在`，与应用约定（`⚠️` 在**正文**开头、标题纯文字）不符。

顺带补上了守卫的漏洞：原来只做字符串匹配，**硬编码的 emoji 抓不到**
（`title=f"{WARN}..."` 能匹配，`title="⚠️..."` 不能），
且只查 `title=` 关键字、漏了 `_notify(正文, 标题)` 这种**位置参数**。
现在从 AST 取标题实参、逐调用声明标题在第几个位置，
并已用"故意埋坏样本"证明它确实会拦。

## 说明

- 除上述两项外，功能与 v1.2.0 完全相同。
- v1.2.0 保持原样不撤回（其标签指向正确的代码提交，
  仅是产物自报版本串里缺少哈希）。
