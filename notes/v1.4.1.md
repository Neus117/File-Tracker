# File Tracker v1.4.1

**修一个会让程序无声消失的崩溃，并查清了一个"回车打开文件夹很卡"的性能问题。**

## 修复

**关闭窗口时，如果还有排队中的"展开目录"事件，进程会直接崩溃。**

表现是**界面突然消失、没有任何报错**（事件查看器里是 `0xC0000005` 访问冲突）。

原因是 `wx.TreeCtrl.Expand()` 会**投递事件**，而 `wx.Window.Destroy()` 是
**延迟销毁**（只打标记，真正释放要等事件循环）。两者叠在一起就会出现
"窗口已标记销毁、队列里还躺着展开事件"的瞬间，处理它就是在访问一个
正在被释放的控件。现在会先确认控件是否还在。

> 顺带记一条踩过的坑：判断"窗口是否已销毁"**要用 `IsBeingDeleted()`，
> 不能用 `GetHandle()`** —— 在"已标记、未释放"的那段窗口里，
> `GetHandle()` 仍然返回有效句柄，查它挡不住（第一版就是这么写错的）。

## 一个查清但**没修**的性能问题

从导航窗格的地址栏输入路径回车，如果那条路径**经过一个大目录**，会明显变卡；
之后关程序也变慢。

**原因已经定位**（实测，`tools/probes/probe_pathbar_cost.py`）：

沿路径展开时，**每一级祖先目录都被完整地建成了树节点，包括里面的所有文件**。
输入 `C:\Windows\System32\drivers\etc` 时：

```
C:\Windows            85 项
C:\Windows\System32   5000+ 项（其中 4700 个是文件）← 对"找下一级"毫无用处
drivers               200 项
etc                   10 项
```

| 指标 | 实测 |
|---|---|
| 这条路径的展开耗时 | 288.9 ms |
| 树节点增长 | **+5783** |
| 关程序（5832 个节点） | **211.2 ms**（空树基线 58 ms） |

**为什么没修**：试了三种"中间层只建目录"的方案，都被 `wx.TreeCtrl` 的机制挡住 ——
它唯一的重建方式是 `DeleteChildren` + 从头插入，而这个动作会
**删掉调用方正拿着的节点**（导致崩溃），或者**删掉已经建好的文件节点**
（导致"点开目录只剩文件夹"）。**这一版选择稳定，把优化留到以后。**

> 如果你遇到这个卡顿：**关掉程序再打开**即可清掉累积的树节点。
> 日常记录量（几十到几百条）不受影响。

**English**

**Fixes a crash that could make the app vanish silently, and documents a
performance problem that was tracked down but deliberately not changed.**

**Fixed**

**If a queued "expand directory" event was still pending while the window was
being destroyed, the process would hit an access violation.**

The symptom was **the window disappearing with no message at all**
(`0xC0000005` in Event Viewer).

The cause: `wx.TreeCtrl.Expand()` **posts an event**, while
`wx.Window.Destroy()` is a **deferred destroy** (it only sets a flag; the real
release happens on a later event-loop turn). When those overlap, the event is
handled against a control that is already being freed. It now checks whether the
control still exists first.

> One gotcha worth recording: to test "is this window already destroyed", use
> **`IsBeingDeleted()`, not `GetHandle()`** — during that "flagged but not freed"
> window, `GetHandle()` still returns a valid handle, so checking it does not
> help (the first attempt did exactly that and still crashed).

**A performance problem that was diagnosed but NOT changed**

Opening a folder from the address bar gets noticeably slow when the path
**passes through a large directory**, and closing the app afterwards is slow too.

**The cause is identified** (measured with `tools/probes/probe_pathbar_cost.py`):
while walking down the path, **every ancestor directory is fully materialised into
tree nodes, including all of its files**. Typing
`C:\Windows\System32\drivers\etc` means:

```
C:\Windows            85 entries
C:\Windows\System32   5000+ entries (4700 of them files) ← useless for "find the next level"
drivers               200 entries
etc                   10 entries
```

| Metric | Measured |
|---|---|
| Expanding that path | 288.9 ms |
| Tree node growth | **+5783** |
| Closing the app (5832 nodes) | **211.2 ms** (empty-tree baseline: 58 ms) |

**Why it was not changed**: three "only build directories in the middle" designs
were tried and all of them ran into `wx.TreeCtrl`'s mechanics — its only way to
rebuild is `DeleteChildren` + fresh inserts, and that action either **deletes
nodes the caller is still holding** (a crash) or **deletes already-built file
nodes** ("the folder opens to show only subfolders"). **This release chooses
stability and leaves the optimisation for later.**

> If you hit this slowdown: **restarting the app** clears the accumulated tree
> nodes. Everyday record counts (tens to hundreds) are unaffected.

**Notes**

- **The UI and the on-disk format are identical to v1.4.0** — just replace the exe.
- Download size is **12.70 MB**, the same as v1.4.0 (behaviour only, no
  dependency changes).
- Automated tests: **200 unit tests + 214 GUI checks** (unchanged from v1.4.0).
- New diagnostic tool `tools/probes/probe_pathbar_cost.py` times the four steps of
  an address-bar Enter, so this class of problem can be measured directly next time.
