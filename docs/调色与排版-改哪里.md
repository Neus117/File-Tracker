## 三、列宽怎么改

列宽有**两个**地方，一个是初始值，一个是运行时的自动调整——**两个都要看**，
否则你改了初始值却发现窗口一出现就被覆盖了。

### ① 初始列宽：`app.py` 第 48 行 `COLUMNS = (`

```python
COLUMNS = (
    ("访问的路径", 400, False),   # ← 括号里第 2 个数就是初始列宽（物理像素）
    ("频次",        80, True),
    ("访问日期",   112, True),
    ("访问时间",   104, True),
)
```

### ② 运行时的自动调整：`app.py` 第 726 行 `def adjust_column_widths`

这个函数在**每次加载数据、改窗口大小**时都会跑，它会用**实际内容**重新算宽度，
所以 ① 里写的数只在"还没有数据"时起作用。

```python
def fitted(column, header, extra=24):        # 第 734 行附近
    """列宽 = max(表头宽, 各单元格宽) + 边距。"""
```

| 想改什么 | 改哪里 |
|---|---|
| **频次/日期/时间列更宽一点** | 第 734 行 `extra=24` 调大（24 是逻辑像素，你屏幕 ×1.75） |
| **路径列保底更宽** | 第 750 行 `path_min_width = 300` |
| **路径列右边少留一点空白** | 第 752 行 `fixed_total + 24` 里的 `24` |
| **完全不要自动调整** | 把 `adjust_column_widths()` 的函数体清空，只留 `self._sync_header()`；这样 ① 里的数就是最终值 |

> ⚠️ **改完列宽必须调 `self._sync_header()`**（第 734 行那段结尾已经有了）。
> 自绘表头是从列表读列宽的，不调的话表头会和下面的列**对不齐**。

**你的屏幕是 175% 缩放**，所以 96 DPI 下的 24 逻辑像素在这里是 42 物理像素。

## 四、深色下的白框与分界线

这两条线的来源**不同**，而且都改不了颜色——因为**都不是 wx 的客户区**。

> **关键概念**：窗口绘制分**客户区**（client area）和
> **非客户区**（non-client area：边框、标题栏、滚动条）。
> `SetBackgroundColour` **只管客户区**。非客户区由**系统主题**绘制，
> 设色一律无效，只能**改样式位**（`wx.BORDER_*` / `WS_BORDER` / `WS_EX_*`）。
>
> 判据要用**几何量**：`窗口矩形宽 − 客户区宽`。
> **别用像素取样**——本环境下不可靠，我为此白跑了好几轮。

### ① 导航窗格四周的白框 → `GenericDirCtrl` 的 2px 非客户区边框

**我在这条上判断错了两次**，如实记录：

| 我的判断 | 结果 |
|---|---|
| ① 内层树的 `WS_EX_CLIENTEDGE` | 去掉后**白框还在** |
| ② `wx.DIRCTRL_3D_INTERNAL` 样式 | 实测**与它无关** |
| ③ **`GenericDirCtrl` 默认带 2px 非客户区边框** | ✅ **是真的** |

实测四个变体（各自独立一个窗口，量"窗口宽 − 客户区宽"）：

| 样式 | 非客户区（每边） |
|---|---|
| `DIRCTRL_MULTIPLE` | 2 px ← **默认就有** |
| `DIRCTRL_MULTIPLE \| DIRCTRL_3D_INTERNAL` | 2 px ← 与 3D 无关 |
| **`DIRCTRL_MULTIPLE \| wx.BORDER_NONE`** | **0 px** ✅ |
| `DIRCTRL_MULTIPLE \| wx.BORDER_SIMPLE` | 1 px |

**位置**：`app.py` 第 **293** 行 —— `style=wx.DIRCTRL_MULTIPLE | wx.BORDER_NONE`

> 顺带：`app._remove_tree_client_edge()`（`app.py` 第 **655** 行）还去掉了内层树的
> `WS_EX_CLIENTEDGE`（另一圈系统画的边）。那条保留着，但它**不是**白框的根因。

### ② 两栏之间的分界线 → wx 自绘的 sash

`wx.SplitterWindow` 的 sash 是 **wx 自己画的**（`wxSashWindow` 那套 3D 绘制），

**当前状态**：`app.py` 第 **254** 行 `splitter.SetSashInvisible(True)` 生效；
第 **425** 行 `self.pane_border = BorderLine(...)` **被注释掉了**
（你自己改的），所以两栏之间现在**没有线**。
验证脚本对此是宽容的——没有 `pane_border` 就只确认 sash 已隐藏，不判失败。

| 想改什么 | 改哪里 |

| **要回那条自绘线** | 取消 `app.py` 第 **425** 行注释 |

### ③ 弹窗的 ⚠️ 前缀，与**为什么必须换成自绘弹窗**

用户要求"在所有警告弹窗的标题前加上 ⚠️"。

**第一件事：系统对话框没法适配深色主题。**

用户反馈"警告弹窗的深色主题适配失败"。原因是
`wx.MessageBox` / `wx.MessageDialog` 在 Windows 上是**系统对话框**
（`MessageBoxIndirect`），由 Windows 按**系统主题**绘制——
`SetBackgroundColour` 无效、`SetPreferredAppMode` 也不管它。
**没有受支持的换肤接口**，所以只能换成自己画的。

> 这条我先写成"已知代价"。**它不是代价，是选错了控件。**
> 想要可控的外观，就不能用系统对话框。

`widgets.py` 里新增 `ThemedDialog`（搜 `class ThemedDialog`）：

* 标题栏**留空**（原生标题栏由系统画，深色下是浅色），标题改成窗口内自己画的粗体文字
* 底色 `theme.background`、正文 `theme.text`
* 「是 / 否」按钮复用 `RoundedButton` —— **外观与主界面完全一致**
* `no_label=None` 时只出一个按钮（纯提示框）

| 弹窗 | 现在的实现 | 加 ⚠️ |
|---|---|---|
| 路径不存在 / 路径失效 | `self._notify(...)`（单按钮） | ✅ |
| 确认删除 / 确认清空 | `ThemedDialog(...)`（是/否） | ✅ |
| **`--version` 的版本信息框** | `ThemedDialog`（单按钮） | ❌ **故意不加**——它是"信息"不是"警告" |
| **数据库打不开** | `wx.MessageBox`（**保留**） | ✅ 有 WARN，但**不能换**——见下 |

**唯一保留 `wx.MessageBox` 的地方**是数据库初始化失败
（`app.py` 第 **101** 行）：那是 `__init__` 早期，`InitUI` 还没跑、
`self` 还不是一个可用窗口（没有 handle），`ThemedDialog(self, ...)` 建不出来。
而且它是**致命错误**，弹完就 `raise`，用户根本看不到主界面——
**不要为了统一外观把这条也换掉，换了会连提示都弹不出来。**

`WARN` 常量在 `app.py` 第 **68** 行（`WARN = "\u26a0\ufe0f"`）。
验证脚本会把**续行拼起来**再扫（多处调用是折行的），确认每个警告弹窗标题
都含 `WARN`，并带两条阳性对照：确实扫到 ≥4 处、"有意不加"的不超过 2 处。

## 五、几个"改了没反应"的坑（都踩过）

### ① 列间竖线：`separator` 改色没变化

**根因不是颜色，是线根本不存在。** 你为此反馈了三次。

`separator` 只画在**表头**里（`header.py` 第 **218** 行），
**数据行里从来没有画过任何竖线**。
`app.py` 的注释里早就写了"改由 `_draw_column_separators` 在客户区自绘竖线"——
**但那个方法我一直没写。**

修法：在 `app.py` 里真正实现（搜 `_draw_column_separators` /
`_paint_column_separators`）：

* 用 `wx.ClientDC(list_ctrl)` 直接往列表客户区画
* 排在本轮绘制**之后**（`CallAfter`），否则会被原生行绘制覆盖
* 只在列边界上画**竖线**，不画横线（你明确说行之间不要线）
* 列宽变化、滚动、重绘之后都要补画一次

验证脚本的判据是**拦截 `wx.ClientDC.DrawLine` 看真的落笔了没有**——
不是"方法存在"、也不是"没报错"。
实测：`DrawLine` 3 次，x = `[843, 931, 1095]`，列边界 = `[845, 933, 1097]`。

> **教训：注释里写"改由 X 负责"之后，必须确认 X 真的存在。**
> 一句没兑现的注释比没有注释更糟——它会让下一个人（包括我自己）
> 以为问题已经处理过了。接线检查能抓"方法没人调用"，
> 但**抓不住"注释里提到了一个不存在的方法"**。

### ② 输入框圆角有锯齿

`wx.DC.DrawRoundedRectangle` 是 **GDI** 调用，**不做抗锯齿**——
圆角是硬边像素，放大看就是台阶。
改成 `wx.GraphicsContext`（`widgets.py` 里 `PathBar.draw`，搜
`必须走 GraphicsContext`）：GC 的 `DrawRoundedRectangle` 带抗锯齿。

> 按钮（`RoundedButton._on_paint`）一直用的就是 GC，所以**只有输入框有锯齿**。

### ③ "清空"按钮的红边

用户先要求"去掉红色边线（不是文字）"，我改成了**完全透明**；
用户随即指出"边缘要和其他按钮一致，要么都有边线，要么都没有"。

两条合起来意思很明确：**红边去掉，但普通按钮那圈边线要保留。**
所以 `RoundedButton._colours()` 里 `variant="danger"` 返回
`theme.border`（= 普通按钮的描边色），文字仍是 `danger` 色。

> **教训**：用户说"去掉 X"时，先想清楚**去掉之后和谁比会不一致**。

### ④ 弹窗验证把脚本挂死

提示框换成 `ThemedDialog` 之后，验证脚本**卡死**在"改动 ④"之后再无输出。
原因：脚本只挡了 `wx.MessageBox`，而 `ThemedDialog.ShowModal()`
**会真的阻塞**等用户点按钮。
修法：拦 `frame._notify`（见 `verify_gui.py` 搜 `original_notify`）。

> **教训：把"弹窗"换成另一种弹窗时，所有"拦截弹窗"的测试代码都要跟着改。**

### ⑤ 表头竖线与数据行竖线错位（粗细也不一致）

用户反馈："检查列标题和列数据分隔线为什么粗细不一致+未对齐"，
并推测是"3D 凹槽绘制问题（列标题不绘制、列数据分隔线绘制了）"。
**方向对了一半**：确实是两条线各画各的，但不是 3D 凹槽。

| | 表头（原来） | 数据行 |
|---|---|---|
| x | `列边界 − 1 − gap`（gap = 6 逻辑像素 ≈ **偏左 10 物理像素**） | 列边界 |
| y | `4 .. height−4`（**上下各空 4**） | `0 .. height`（满高） |

所以既错位又不等长。**两处各算各的**就是这个 bug 的成因。

修法：让位置**只有一个来源** ——
`header.ColumnHeader.separator_positions()`（搜这个方法），
`_on_paint` 直接取用它的结果、**不再重算**；
数据行的 `app._paint_column_separators` 用同一条规则；
粗细两边都取 `separator_thickness()`。

> **教训：同一份几何算法不要在两个地方各写一遍。**
> 复制出来的第二份迟早与第一份不同步——这正是本 bug 的成因。
> 接线检查能抓"方法没人调用"，但**抓不住"两处各实现了一遍"**。

### ⑥ 列表文字颜色改不动（我改错了对象）

用户要求"路径记录文字恢复纯黑/纯白"。我原本想"路径列黑、其余列灰"，
写了先设路径列、再循环设其它列——**后者把前者覆盖了**，整行都是灰的。

根因：**`wx.ListCtrl` 的文字颜色是按行的，没有按列版本**
（见 `tools/probes/probe_item_colour.py` 的实测表：
`ItemAttr.SetTextColour(colour)` 无列参数、虚拟列表 `OnGetItemAttr(item)`
也只有 item、`ListCtrl` 里不存在含 `Column`+`Attr` 的方法）。

修法：**整行统一用 `theme.list_text`（纯黑 `#000000` / 纯白 `#FFFFFF`）**。
`list_text` 与 `text` 刻意分成两个字段：`text` 还管表头/弹窗/按钮，
`list_text` 只给列表内容。

### ⑦ 弹窗太小 / 不好看 —— 去读了 Roboc 的源码

用户问："**Roboc 的所有窗口外观为什么规范又漂亮啊？你能找找原因吗？**"

去读了 `D:\Coding\MyGitHub\Roboc\src\Roboc.App\MessageDialog.cs` 与
`ProgressTheme.cs`、`RoundedBox.cs`，原因很明确：

> **它不用任何自动布局。所有位置和尺寸都按一个固定公式手算。**

```csharp
int margin       = Scaled(24, dpi);      // 逻辑像素 → 物理
int maxTextWidth = Scaled(420, dpi);
int buttonHeight = Scaled(32, dpi);
int buttonWidth  = Scaled(96, dpi);
int gap          = Scaled(8, dpi);
int buttonsWidth = labels * buttonWidth + (labels - 1) * gap;
int bodyTop      = Scaled(24, dpi);
int buttonsTop   = bodyTop + bodyHeight + Scaled(28, dpi);
int clientWidth  = Max(maxTextWidth, buttonsWidth) + margin * 2;
int clientHeight = buttonsTop + buttonHeight + Scaled(20, dpi);
int left = clientWidth - margin - buttonsWidth;   // 按钮右对齐
```

三条可以直接搬的规律：

1. **别用 `Fit()`。** 自动布局把"内容多宽"和"窗口多宽"绑死，
   长一点的消息就撑出一个又宽又矮的窗口（我原来那版是 455×228）。
   固定公式让宽高比始终正常。
2. **不要自己加标题行。** 原生确认框的标题在**标题栏**里，
   正文区只有消息 + 按钮。我加的粗体标题是多余的第四层——
   这就是"越改越雷霆"的直接原因。
3. **外边距一律 24 逻辑像素**，不是 8 也不是 12——
   它给正文留出呼吸感，这正是"挤"和"不挤"的分界。

本项目的 `widgets.ThemedDialog._layout()` 就是上面那段公式的 Python 版，
数值一个不改（`theme.METRICS` 里的 `dialog_*` 系列）。
实测 **819×210**（= (420 + 24×2) × 1.75），与 Roboc 同尺寸。

**Roboc 另外两条与本项目无关但值得记的：**

* 圆角**必须用 GDI+ `GraphicsPath` + `AntiAlias`**，不能用 GDI region
  （`CreateRoundRectRgn`）——region 是"像素集合"不是几何形状，
  没有半像素概念，圆角只能是台阶。本项目的 `wx.GraphicsContext`
  就是同一回事（见上面第 ② 条）。
* 标题栏用 `DwmSetWindowAttribute(35, ...)` 设成**比卡片暗 10~12 级**，
  不是完全相同——完全相同会让窗口读成"一整块 + 一个关闭按钮"，
  没有可拖拽区的暗示。本项目是 `win32.set_title_bar_dark`。

**踩到的两个 wx 坑**（都实测过）：

* 不给 `wx.Dialog` 装 sizer 时，`Show()` 会把**唯一的**子控件拉满客户区
  （单按钮弹窗的按钮变成 819×210，双按钮反而正常）。
  装一个"空 sizer"也不行——sizer 会把按钮重排到 x=0。
  最终解法：**单按钮时加一个 1×1 的隐形占位控件**。
* `frame.GetDPI()` 返回的是 `wx.Size`，而 **`wx.Size` 不是 `tuple`**，
  `isinstance(x, (tuple, list))` 判不出来 —— 传进 `scale_for_dpi`
  会在 `dpi <= 0` 那里 TypeError。

### ⑧ 第二轮对比：弹窗还是不像 —— 两个"看着像空壳"的原因

用户把 Roboc 与自己的弹窗并排截图，说"不知道你能不能看出差距"。
抓图逐像素核对后，找到**两个**都会让弹窗看起来只剩一个空壳的原因：

**① 没有标题栏。** 我用的是 `wx.BORDER_NONE` —— 没有标题、没有关闭按钮、
没有可拖拽区，看着就是一个方块。Roboc 是（`MessageDialog.cs` L209）：

```csharp
uint style = WS_OVERLAPPED | WS_CAPTION | WS_SYSMENU;
```

wx 的等价物是 **`wx.DEFAULT_DIALOG_STYLE`**
（实测 = `CAPTION | SYSTEM_MENU | CLOSE_BOX | TAB_TRAVERSAL` = `0x20001800`）。
Roboc 还用 `AdjustWindowRectExForDpi` 把客户区尺寸换算成窗口尺寸；
wx 的 `SetClientSize` 做的就是同一件事 —— 实测
**客户区 819×210 → 窗口 843×266**（多出来的 56 像素就是标题栏 + 边框）。

**② 没设 `BG_STYLE_PAINT`，`AutoBufferedPaintDC` 直接抛断言。**

```
wxAssertionError: "win->GetBackgroundStyle() == wxBG_STYLE_PAINT" failed
    at ...dcbuffer.h(230) in wxAutoBufferedPaintDC::wxAutoBufferedPaintDC()
```

那个断言是**静默的**（wx 吞掉异常、只打 traceback），表现就是
**正文一个字都画不出来**。所以 `__init__` 里必须有一行
`self.SetBackgroundStyle(wx.BG_STYLE_PAINT)`。

**③ 顺带：`DrawLabel` 画不出文字。** 直接换成逐行 `wx.DC.DrawText`。
（`wx.DC` 在 Python 侧没有带宽度约束的测量/绘制：
`GetMultiLineTextExtent()` 不收宽度参数、`DrawText()` 只接受 `(text, x, y)`、
`DrawLabel()` 在对话框上实测一个字都没有。所以折行是自己写的，
见 `ThemedDialog._wrap_lines`，等价于 Roboc 的 `DT_WORDBREAK`。）

> **教训：验证脚本原来只查"矩形算得对不对"，查不出"这段代码根本没跑"。**
> 现在加了三条判据：标题栏样式位、`BG_STYLE_PAINT`、
> 以及**在位图上数正文区的暗像素**（正向证据）。

### ⑨ 分隔线改成"最细"：**1 物理像素，不按 DPI 缩放**

用户要求："将列分隔线改细。最细。"

关键点：`separator_thickness` **不能**按 DPI 换算。

| | 值 |
|---|---|
| `METRICS.separator_thickness` | `1` |
| 旧算法 `scale_for_dpi(1, 168)` | **2** ← 用户嫌粗的那个 |
| 现算法 | **1 物理像素** |

理由：**1 像素的细线是显示器的属性，不是内容的属性。**
字号、按钮高度、边距要随 DPI 放大（否则在高分屏上小得看不清），
但"一条 1 像素的线"在任何 DPI 下都应该是 1 像素。

所以 `header.separator_thickness()` 与
`app._paint_column_separators` 都**直接取常量、不做换算**。

### ⑩ 弹窗：⚠️ 从标题栏搬到正文，标题栏换成程序图标

用户要求："标题栏题头的 ⚠️ 换成程序图标，把 ⚠️ 放在说明文字的前面，和 Roboc 一致。"

**Roboc 的约定**（去源码里确认过）：

| 位置 | 内容 |
|---|---|
| 标题栏 | 应用名 + 描述，如 `"Roboc — 注册失败"`（`Program.cs` L210） |
| 正文开头 | `⚠️`（`Program.cs` L200、`ProgressWindow.cs` L469 都是 `$"⚠️确定要…"`） |
| 标题栏左侧 | 程序图标——`hIcon = AppIcon.Handle`（`MessageDialog.cs` L134），注释写着 "a class registered without an icon gives a window without one" |

本项目的对应改动：

* `WARN` 从 `title=f"{WARN}确认清空"` 改成正文前缀
  —— 统一由 `FileTracker._notify` 加（`f"{WARN} {message}"`），
  两个确认框在调用处直接写进正文
* `ThemedDialog._apply_icon()` **显式设图标**：
  `wx.Dialog` **不会**自动继承父窗口的图标，实测不设的话标题栏左侧是空白
  （先试 `parent.GetIcon()`，拿不到再从 `images/shell32_star.ico` 读）

验证脚本的对应判据也换了：

```
[PASS] 所有警告/确认弹窗都在**正文**里带 ⚠️（Roboc 的做法）
[PASS] 阳性对照：没有任何弹窗把 ⚠️ 留在标题里
[PASS] 弹窗标题栏有程序图标
[PASS] ⚠️ 在正文开头（Roboc 的做法），标题是纯文字
```

> **顺带把"扫弹窗"的实现换成了 `ast`。**
> 原来用"按括号配平拼续行"的土办法，被折行调用、`def` 定义行、
> `except ...: # 注释` 三种情况轮番坑，报出"扫到 1 处、其余 3 处"全是误报。
> `ast` 直接给出真实的 `Call` 节点，注释与字符串天然被排除
> —— 与 `tools/check_wiring.py` 用的是同一招。

### ⑫ 预选跟随（hot tracking）：我第一版用错了标志

用户把需求解释得很准确：

> 假设选中色有两档，高亮和次级高亮，鼠标左键单击后为高亮，
> 鼠标移到目标上方不单击为次级高亮，这就是预选状态。

官方术语这叫 **hot tracking**。查
[Extended List-View Styles](https://learn.microsoft.com/en-us/windows/win32/controls/extended-list-view-styles)，
两个标志的措辞**完全不同**：

| 标志 | 官方描述 | 结果 |
|---|---|---|
| `LVS_EX_TRACKSELECT` | "an item is **automatically selected** when the cursor remains over the item **for a certain period of time**" | ❌ 带定时器会慢；悬停久了**真的选中** |
| `LVS_EX_TWOCLICKACTIVATE` | "This style **also enables _hot tracking_** ... Hot tracking means that when the cursor moves over an item, **it is highlighted but not selected**" | ✅ 正是"预选" |

**我第一版开的是 `LVS_EX_TRACKSELECT`。** 用户实测："反应特别慢，
有近一秒的延迟，这是严重的性能问题，说明方法不对。"

**他判断得对。** 那个延迟来自它自带的定时器
（[`LVM_SETHOVERTIME`](https://learn.microsoft.com/en-us/windows/win32/controls/lvm-sethovertime)
/ 系统默认 `SPI_GETMOUSEHOVERTIME`，本机实测 100 ms），
而且它把"预选"和"选中"**混成了一档**——正好是用户说的"两档"里少掉的那一档。

现在的分工：

| 档 | 谁画 | 颜色 |
|---|---|---|
| 预选（悬停跟随） | **控件**（`LVS_EX_TWOCLICKACTIVATE` 的热跟踪） | 系统次级高亮 |
| 选中（单击之后） | **本项目**（`_apply_selection_highlight`） | `SYS_COLOUR_HIGHLIGHT` = `#0078D7` |

**为什么不加 `LVS_EX_ONECLICKACTIVATE`**：它同样 enables hot tracking，
但会把**单击**变成激活（直接打开文件夹），改掉用户习惯的单击选中。
用户要的是"双击/打开"才打开，所以取两击那一档。
实测确认：加了 `TWOCLICKACTIVATE` 之后
3 次双击 → 3 次 `on_item_activated`，单击仍然只是选中。

> **`SendMessageW` 的签名坑**：ctypes 默认按 32 位整数解释返回值，
> 读取长消息会静默截断——我量 `LVM_GETHOVERTIME` 时读回恒为 0，
> 差点据此得出"这个 API 不可用"的错误结论。
> 必须显式声明 `argtypes` / `restype`。

### ⑬ 预选跟随最终版：**不依赖原生热跟踪，自己画**

这一条前后错了三次，每次都是用户实测推翻的：

| 版本 | 做法 | 用户实测反馈 |
|---|---|---|
| 一 | `LVS_EX_TRACKSELECT` | "反应特别慢，有近一秒的延迟，说明方法不对" |
| 二 | `LVS_EX_TWOCLICKACTIVATE` | "浅色主题依旧没有预选跟随，深色依旧有" |
| 三 | **自绘 `theme.row_hover`** | — |

**每次错的都是同一个念头：指望系统替我画。**
原生热跟踪的颜色随主题而变，第三方既拿不到也改不了。

现在两档全部由本项目说了算：

| 档 | 触发 | 底色 | 谁画 |
|---|---|---|---|
| 预选（次级高亮） | `EVT_MOTION` | `theme.row_hover`（`#DCE9F7` / `#2B4A66`） | 本项目 |
| 选中（高亮） | 单击 / 键盘 | `SYS_COLOUR_HIGHLIGHT`（`#0078D7`） | 本项目 |

选中优先于预选。三个原生热跟踪标志**全部关掉**并在读回时校验。

**性能**：用户上一轮指出过延迟问题，所以
`_apply_selection_highlight` 有两条短路——
行号没变就直接返回，变了也只重画**受影响的几行**，
不整表重绘。

**验证**：`tools/probes/probe_two_tier_highlight.py` 跑两个主题各一遍，
四个场景（初始 / 只悬停 / 两档同时 / 选中优先 / 离开还原）全部通过。
判据用**属性回读**，不用像素。

### ⑯ 所有按钮圆角收一档 + 描边被裁断

用户："所有按钮圆角过大，统一参数、适当缩小圆角；
按钮边缘线右侧有被裁断痕迹，roboc 里是没有这种情况的。"

#### ① 圆角一路收到 5，并从"比例"改成"绝对值"

用户逐次要求：8 →（"圆角过大"）→ 6 →（"继续收到 5"）。

| | 取值 | 本机 175% 下物理半径 |
|---|---|---|
| 最初 | 4 / 12 / 8 | — |
| 上一版 | 6（比例 1/4） | 10 px |
| 上一版 | 5 / 6 | 9 / 10 px |
| **现在** | **8（用户自己改定）** | **14 px** |

**顺带修掉一个与"统一参数"矛盾的地方。** 原来用**比例**
（`radius_button_ratio`），只有高度恰好的整数倍时才得到目标半径，
其它高度会因取整差 1 —— **不同按钮的实际圆角就不一样**。

改成**绝对值** `radius_button` 之后，任何高度的按钮圆角都是同一个数。
用户随后在 5 与 6 之间比较，**最终确定 6**：
验证脚本的判据也跟着换了：

```
[PASS] 按钮圆角取自 METRICS.radius_button（单一来源，可调）
[PASS] 所有按钮圆角完全相同（绝对值，不随高度变）
[PASS] 半径不超过半高（极小按钮不会畸形）
```

> **判据本身改了一次。** 原来断言"半径 == 5"（硬编码字面数字），
> 用户一回调到 6 就误报失败。但"半径等于多少"**不是运行时契约**，
> 它就是个可调参数；该守的是"绘制用的半径确实来自这个常量"。
> 现在判据绑常量、并断言源码里读的就是它。

> 附：Win11 原生按钮是固定的 **4 物理像素**、不随 DPI 变；
> 本项目按逻辑像素 × DPI 走，5 逻辑 ≈ 9 物理。

#### ② 右侧被裁断——**描边中心线画在了客户区边缘**

根因：`gc.DrawRoundedRectangle(0, 0, w, h, r)` 画的是**路径**，
1px 描边以路径为**中心**向两侧各扩 0.5。于是

```
右边界线覆盖 [w - 0.5, w + 0.5)
客户区只有  [0,     w)
                      ↑ 外半像素落在窗口外，被裁掉
```

看上去就是"线断了一截、颜色变淡"。

**修法**：整体内缩半个笔宽，让描边**完全落在客户区内**：

```python
pen_width = pen.GetWidth() if draw_border else 1
inset = pen_width / 2.0
gc.DrawRoundedRectangle(inset, inset,
                        width - pen_width, height - pen_width,
                        max(self._radius - inset, 1))
```

> 项目里 **`PathBar` 早就是这么做的**（`x-1, w+2` 外扩来容纳描边），
> 只有 `RoundedButton` 漏了——所以锯齿/裁断问题只出在按钮上。

#### ③ 右边"裁断感"的真正根因：**平移了半像素 / 一像素**

第一版内缩半个笔宽、第二版内缩整整一个笔宽，用户两次都说
"右边仍有裁断感（比之前好一些，但没完全解决）"。

把各种 `(inset, 矩形宽)` 组合全画一遍
（`tools/probes/probe_stroke_raster.py`），规则才浮出来：

| inset | 矩形 | 左列 | 右列 | 结果 |
|---|---|---|---|---|
| 0 | 189×42（=位图尺寸） | 0 | **无** | ❌ 右支完全落在位图外 |
| **0** | **188×41** | **0:255** | **188:255** | ✅ **唯一全对** |
| 1 | 187×40 | 1:255 | 188:255 | ❌ 左 1 右 0，差一列 |

**规则**：描边**外边缘**落在 `x`，覆盖 `[x, x+1)`。
想让最外那一列**满覆盖**，路径必须正好在 0，
且描边带的右边缘不越过 `W` ⇒ **矩形取 `(W-1) × (H-1)`，一点不平移**。

我前两版都错在**平移**上——平移会让边界落在像素中间，
抗锯齿把覆盖分摊到相邻两列，看上去就是"边缘淡了一层 / 断了一截"。

**另有一处**：`accent` 按钮的"描边色"就是它自己的底色，
却也被当成描边处理，于是纯色实心块四周留了一圈透出父窗口的缝。
现在**填充与描边分两步**：填充铺满 `[0, W]`，描边只在颜色与填充
**不同**时才画。

**验证**（`tools/probes/probe_button_edge_columns.py`）：

```
accent   同一深度的左右差 = [0,0,0,0,0,0,0,0]  ✅ 镜像对称   最外列覆盖 1.00 / 1.00
secondary 同一深度的左右差 = [0,0,0,0,0,0,0,0]  ✅ 镜像对称   最外列覆盖 1.00 / 1.00
```

> **判据本身踩过一个坑**：最初只比"最外一圈四条边颜色是否相同"，
> 那个判据在**整块图形偏移半像素**时也成立。必须**逐列镜像比较**。
> 另外右边要从 `x = W-1-i` 取，与左边 `x = i` 同深度——
> 我第一版两边起点不对应，于是"恒定差 1 列"，**无论画得对不对都报错**。

### ⑮ 提示窗内容居中

用户要求："现在让所有提示窗内容居中显示。"

**正文逐行居中**，**按钮组整体居中**。为此宽度公式也跟着改了：

| | 改前 | 改后 |
|---|---|---|
| 宽度 | 固定 `max_text_width + margin×2`（175% 下恒 **819**） | `max(正文实宽, 按钮组宽) + margin×2` |
| `max_text_width` | 固定宽度 | **退化为上限**（超过它才折行） |
| 正文 | 左对齐 | **每行各自居中** |
| 按钮 | 右对齐 | **整组居中** |

**为什么要一起改宽度**：Roboc 固定取 420 逻辑像素，文字排不满时
右侧留一大块空白。内容一居中，那块空白就变成**两边都空**，更难看。
实测短消息的弹窗从 `819×210` 收到 `434×210`。

> 只是**排版选择**不同，间距节奏（24 / 32 / 8 / 28 / 20）一个没动。

**验证**（`tools/probes/probe_dialog_center.py`，几何判据）：

| 场景 | 结果 |
|---|---|
| 短消息（单行） | 正文左右留白差 **1 px**，按钮组左右各 42 |
| 多行消息（5 行含空行） | 每行各自居中，最大差 **1 px** |
| 超长消息（折行） | 4 行，最大差 **1 px**，且正文高正好装进正文区 |

验证脚本的对应判据也换了——**不能再断言宽度恒为 819**：

```
[PASS] 弹窗宽度按**实际文字**算（不再固定 819，也不超过上限）
[PASS] 正文每一行都居中（左右留白相等）
[PASS] 阳性对照：正文确实有内容（不是空行凑出来的居中）
[PASS] 弹窗按钮组居中（左右留白相等）
```

那个"阳性对照"是必要的：全是空行的话左右留白也相等，
**居中的判据会被空内容蒙混过关**，所以要另外证明正文真的有宽度。

### ⑭ 关于"Windows 11 深色主题会自动给第三方窗口加预选跟随"

用户的推测是："深色主题下的 Windows 11，会为所有（包括第三方程序）
类 Explorer 窗口添加预选跟随的效果。"

**查证结果：不成立。** 热跟踪必须由程序自己开

### ⑪ 关于"看图"：本环境的抓图结论大半不可信

这一轮我因为轻信抓图得出了**两次错误结论**，写在这里免得再犯：

| 方式 | 可信度 |
|---|---|
| `WM_PRINTCLIENT` | 全黑 |
| `PrintWindow` | **纯色窗口上通过**，但真实对话框会**丢客户区正文** |

所以"画得对不对"要用后者。见

### ⑳ 设置窗口：标签被按钮压住

用户截图："题头和按钮挤在一起了。"

三个标签（界面语言 / 排序方式 / 排序方向）的最后两三个字被按钮盖住。
**根因有两条，都不在"按钮画得不对"上**：

**① `GetBestSize()` 是旧字体下的缓存值。**

wx 在控件**创建时**按当时的字体算好尺寸并缓存。而
`app._apply_body_font()` 里有一句**类级**的
``wx.StaticText.SetFont(self, body)`` —— 那个 `self` 只用来取"窗口类"，
效果是**类级**的：之后创建的所有 StaticText 都变成 10pt。

于是布局按 9pt 量出的 85 像素给标签留位，而文字按 10pt 画出 ~100 —— 压住。

修法：`_label_width()` 用 `GetTextExtent` **按标签当前的字体现量**，
不再用缓存值。

**② 摆放与测量用的不是同一个宽度。**

`_place_rows` 拿 `_body_rect` 的右边界右对齐，而各行实际只分配到
`content_width` —— 两者差一个 margin（本机 42 像素）。按钮因此比
"标签与按钮共用的那片区域"往左多占了 42。

修法：`_layout` 把 `content_width` **传进** `_place_rows`，两处同一个数。

**顺带定下"标签与按钮同行还是分两行"的规则**，并与算高度的代码**共用**
同一个函数 `_row_lines()`：放不下就标签独占一行、按钮另起一行。
判据写在两处就会分叉——本项目已经因为"两处实现"修过好几次。

`dialog_row_width` 由 240 改到 **300**：240 时标签与按钮放不下同一行
（三行变六行、高到 616）；420 时四个按钮挤进一行（弹窗 897 宽，横带）；
400 时折成 `[3, 1]` 参差不齐；**300 折成 2×2、标签与首行同行，533×434**。
