### ❌ 唯一未解决的 bug

**症状**：从导航窗格打开（「打开」按钮，或双击树里的文件）之后，
记录列表里那条**渲染成浅灰色**，而不是蓝色。

**已经排除的（都有实测证据，别再重复查）**：

| 曾经的理论 | 实测结果 |
|---|---|
| 焦点不在列表 ⇒ 系统画 inactive 灰 | ❌ **诊断输出：焦点 = `ListCtrl`** |
| `_apply_selection_highlight` 的记忆化早退（`_paint_key`）吃掉了重画 | ❌ 已加 `self._paint_key = None`，**仍然灰** |
| 选中落到了别的行 | ❌ **`GetFirstSelected()` = 31，正确** |
| 颜色没设上 | ❌ **`GetItemBackgroundColour(31)` = `#0078D7`** |

**关键事实（用户实测 + 程序自报）**：

```
[focus] record_accessed_path('E:\\Games')
[focus]   _focus_pane = 'tree'  ⇒ from_tree = True
[focus]   调用前 焦点 = DirectoryTree
[focus]   调用后 焦点 = ListCtrl          ← 焦点确实给了列表
[focus]   列表选中 = 31  行底色 = #0078D7  ← 选中对、颜色也设对了
```

**但用户截图里那条是浅灰。** ⇒ **在"程序打印"之后、"画面呈现"之前，有东西把那一行改回了灰色。**

**浅灰在本项目里 = `theme.row_hover`（"预选"那一档）**，
而 `_apply_selection_highlight()` 是**同时管两档**的（选中 / 悬停）。

**下一步（务必这样做，不要再写探针猜）**：

给 `SetItemBackgroundColour` 装一个**记录器**（包装成 wrapper），
在 `FT_DEBUG_FOCUS` 打开时打印**每一次调用的 (行号, 颜色, 调用栈)**，
然后让用户复现一次 → **一眼就能看出是谁在什么时候把第 31 行改回灰的**。

**为什么必须插桩而不是写探针**：我已经写了**七个探针**，每一个都是绿的，
而用户看到的始终不变。**探针复刻的是我以为的场景，不是他的场景。**

## 五、这一轮踩坑的规律（比代码更重要）

### 1. 探针反复"绿"而用户反复说"没变" ⇒ **停止写探针，去他的环境插桩**

我写了七个探针、返工七次，**最后一个诊断打印一次就推翻了两个理论**。
**判据**：当你的仪器和用户的观察长期矛盾时，**问题在仪器的场景，不在被测对象**。

### 2. 仪器读的是"存了什么"，用户看的是"画成什么"

`GetItemBackgroundColour()` 返回 `#0078D7` 与"屏幕上是不是蓝的"**是两件事**。
失去焦点、被别的东西覆盖等等，都会让两者不一致。
**纯几何/属性读回能证明"设对了"，不能证明"画对了"。**

### 3. 记忆化 / 缓存类缺陷，探针**连续操作两次**才可能暴露

`_paint_key` 那种"key 一样就早退"的逻辑，**每个探针都是全新进程、账本从空开始**，
所以**结构上就测不到**。要测它，必须让同一个进程连续走两遍同一流程。

### 4. 用文本特征定位替换 = 危险

- 本会话**两次**因为"`replace(..., 1)` 匹配到了另一处相同文本"而改错地方
- 一次**只搬了一半的代码**（`if override:` 搬走、`override = getattr(...)` 留下），
  代码直接 `NameError` —— **靠动手前的备份回滚的**
- **规矩**：替换前**先数一下这段文本出现几次**；改前**一定留备份**；
  能按行号/按函数定位就**不要用文本特征**

### 5. 同一个概念有两处实现 ⇒ 必然有一处是错的

本轮实例：`_remember_view` 被调两次、`on_pin`/`on_unpin` 共用"保持视角"、
`_render_rows` 与 `_render_rows_body` 各有一份取锚点的代码。

### 6. `Freeze` 里只允许**改内容**，不允许**读状态**

冻结期间 `GetTopItem()` 返回旧值、`ScrollLines()` 不生效 ——
"恢复滚动位置"那一段会**静默失效**。回位必须放到 `Thaw` 之后。
