## 二、四项改动

### ① 初始窗口增大 15% —— 完成

`1280×720 → 1472×828`，并按显示器工作区自动夹取。

**为什么要夹取**：`wx.Display.GetClientArea()` 返回的是**物理像素**
（本机实测 175% 缩放下是 2560×1516），在 1366×768 的笔记本上 1472×828 会超出屏幕。
`fit_window_size()` 取 `min(期望, 工作区 − 边距)`，屏幕够大时原样保留。

**实测证据**（`tools/verify_gui.ps1`）：

```
[PASS] 窗口尺寸 = 1280x720 的 115%      期望 1472x828，实测 1472x828
[PASS] 阳性对照：新尺寸 != 旧尺寸 1280x720
[PASS] 窗口完整落在显示器工作区内        窗口 1472x828，工作区 2560x1516
```

### ② Win11 风格美化 —— 按 Roboc 规范完成，等用户的美学规范

用户选择"先照 Roboc 的视觉规范做，之后再按我的规范改"。落实的是规范里
**与语言无关**的那几条：

| 规范条目 | 落实方式 |
|---|---|
| 配色从系统读取，不写死 | 读 `AppsUseLightTheme` 与 `AccentColor`（**ABGR，需按字节拆**） |
| 字号以磅声明，正文 = 系统 UI 字号 | 取 `SYS_DEFAULT_GUI_FONT` 磅值 +1，不写死像素 |
| 强调色只给"程序推荐的那一个动作" | 只有"打开"按钮用强调色；"清空"用危险色 |
| Win11 圆角 | `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` + 自绘圆角 |
| 自绘必须双缓冲 | `wx.AutoBufferedPaintDC` |
| 深色主题要给标题栏单独声明 | `DWMWA_USE_IMMERSIVE_DARK_MODE`（先试 20，失败再试 19） |

**没有沿用**的：纵向节奏表、速率曲线、固定尺寸对话框——那些是 Roboc 与其
具体窗口绑定的，File Tracker 是可调尺寸的文档窗口。

**实测证据**：配色读出来了（本机强调色 `#2959CC`，即系统色而非写死的蓝），
圆角被 DWM 接受，正文字号 10pt vs 系统 UI 9pt。

> **仍是未验证的部分**：美化里"看着好不好看"这一半我只能读到数值。
> 配色、间距、绘制细节需要用户看一眼。等用户的美学规范到了会再调一轮。

### ③ 频次列数字居中 —— 完成，但**没有走原计划的那条路**

文档给的方案是原生 `LVM_SETCOLUMN`。**实测这条路在本环境上不通**，证据链：

1. `LVM_SETCOLUMN` 一律返回 0（失败），不论结构体字段顺序怎么调、
   不论用 `ctypes` 还是 `pywin32` 封送
2. **用 `CreateWindowExW` 建一个完全不涉及 wx 的裸 `SysListView32`，
   同样的调用同样返回 0**（`tools/probes/probe_native_lvm.py`）
   ——所以这不是 wx 的包装问题
3. 改用像素对照时，**同格式连拍两次就有 21672 个像素不同**，
   而 LEFT vs CENTER 是 21671——信噪比不足以支撑判断
   （`tools/probes/probe_render_noise.py`）

**所以改用 `wx.dataview.DataViewListCtrl`**：它的列对齐是 wx 自己的实现，
不依赖原生消息，而且 **`GetColumn().GetAlignment()` 可以直接回读**——
判据从"没报错"变成了一个能断言的数值。

**实测证据**：

```
[PASS] 频次列（第 1 列）对齐方式 = 居中     align=2304（wx.ALIGN_CENTER=2304）
[PASS] 阳性对照：路径列仍是左对齐            align=0（不是整体居中）
[PASS] 被居中的那一列表头确实是「频次」
[PASS] center_frequency_column() 自检通过    回读确认，不是"没报错"
```

**顺带解决**：`DataViewListCtrl` 没有 `SetRowBackground`，顶置行的浅黄底
改由重写 `OnGetItemAttr` 提供（已实测背景色为 `(255,255,200,255)`）。

### ④ 地址栏 —— 完成

粘贴/输入路径 → 回车 → 展开目录树到该位置 → **记录一次访问**（用户选择"与双击等同"）。
支持 `Ctrl+L` 聚焦、接受"复制为路径"带引号的形式与正斜杠。

**实测证据**：

```
[PASS] 回车后该路径被记录，频次 +1        频次 0 -> 1
[PASS] 目录树选中了目标路径，且恰好一个匹配
[PASS] 列表里出现该行
[PASS] 阳性对照：不存在的路径不产生记录
```

## 三、验证过程中抓出的三个真实缺陷

**这三个都不是读代码找出来的，是"走用户真实那条路"时暴露的。**
正好对应 `01-反复犯的错.md` 的第一条与第七条。

### 缺陷一：`set_icon` 从来没有被调用

删掉重复定义后，新的 `set_icon` **一个调用点都没有**——"从源码运行有图标"
这个被列为本轮第 1 优先级的修复，实现完了却没有生效。

是**接线检查**抓出来的（它报 `无人调用的方法: app.py:152 set_icon`）。
修法是在 `__init__` 里、`InitUI` 之前调用它。

> 这条很值得记：**"我修好了"和"修复生效了"之间隔着一次真正的运行。**

### 缺陷二：地址栏导航后目录树有两项同时高亮

目录树带了 `wx.DIRCTRL_MULTIPLE`，是**多选**控件，而 `SelectItem` 在多选树上
是**追加**而不是替换。于是原有选中项（通常是当前盘符）会一直留着。

`tools/probes/probe_multiselect.py` 单独复现了这一点：
连续 `SelectItem` 三次，`GetSelections()` 返回三项。修法是先 `UnselectAll()`。

> 这条是被"恰好一个匹配"这个**收紧过的断言**抓出来的。
> 第一版断言只要求"选中项里包含目标"，它通过了；收紧之后才暴露。

### 缺陷三：产物 `--version` 输出为空，而构建脚本没报错

单文件 exe 是 **windowed 子系统，没有控制台**，`print()` 直接抛
`OSError: [Errno 22] Invalid argument`。构建脚本当时用 `& $exe --version` 取值，
拿到空字符串，**而脚本没有断言输出非空**——于是一次"成功"的构建掩盖了
"产物不会自报版本"这个事实。

修了三处：

1. `--version` 走 `_emit_or_log()`：写不出 stdout 就落到 `%APPDATA%\File Tracker\version.txt`，
   并在窗口模式弹一个提示框
2. 构建脚本改用 `ProcessStartInfo` 抓输出，并**新增"输出不得为空"的断言**
3. `_report_resource_error` 也加了 `try/except OSError`——它原来也用 `print`

> **同一类错误在同一个脚本里出现了两次**（读为空、以及读操作可能把脚本卡住），
> 值得记：**"没报错"从来不是判据，判据是"值对不对"。**

## 四、接线检查门禁：三轮才做对，而且它自己也被验证过

这是本轮投入最多的一件事，也最值得写下来。

| 轮次 | 做法 | 结果 |
|---|---|---|
| 1 | PowerShell + 正则数名字出现次数 | **78 处误报** |
| 2 | 加否定回顾 `(?<![\w.])name\s*\(` | 仍然误报——这个回顾**恰好排除了 `self.name(`**，而那是 Python 里最常见的调用形式 |
| 3 | 改走 `ast`，区分 Load/Store 上下文 | 正确 |

**第 2 轮的根因值得单独记**：我加了一条"更精确"的否定回顾，它排除的正是
最主流的写法。**这就是"看起来更严谨的改动"反而更坏的一个实例。**

**顺带发现的编码问题**：Windows PowerShell 5.1 读**没有 BOM 的 UTF-8** 文件时
按 ANSI（本机 GBK）解码。Python 源码不带 BOM，于是所有中文变乱码，行列号全错。
这是放弃 PS 版、改写成 Python 的直接原因。

### 门禁自己被验证过

`tools/check_wiring_negative.py` 往临时仓库副本里注入三类缺陷，
断言检查器返回非零且报错指向正确的东西：

```
[PASS] 无人调用的方法 —— 检查器拦住了，且报错指向正确的东西
[PASS] 无人读取的常量 —— 检查器拦住了，且报错指向正确的东西
[PASS] 代码里硬编码开发机路径 —— 检查器拦住了，且报错指向正确的东西
```

**这个阳性对照自己也修过一次**：第一版把带缩进的 `def` 直接追加到文件末尾，
那不是合法 Python，检查器报的是语法错误。于是阳性对照的输出是
"拦住了但报错内容不符"——**看起来像检查器坏了，其实是我造的样本坏了**。
现在注入后会先 `ast.parse` 一次自检。

**阳性对照还抓出了检查器自己的两个漏洞**：

- 只在 `src/` 里找引用 → `PathStore.replace_all` 与 `PathStore.count`
  被误报成死代码（它们是只有测试在调用的公开接口）。修法：测试也是调用点。
- 把所有 `ast.Name` 都算引用 → **一个常量只要被定义出来就算"被引用了"**，
  注入的孤儿常量抓不到。修法：只认 `ctx is Load`。

> 这两个漏洞都是"注入一个必然被拦的样本"才暴露的。**没有一个是我读代码看出来的。**

# 八、第二轮：用户实测反馈后的修正

用户跑过之后提了五条。**四条是真实缺陷，一条是我理解错了。** 逐条记录根因。

## 反馈一：「未响应，需要我终止它吗？」—— 我的验证脚本把窗口挂在用户屏幕上

**这是本轮最严重的问题**，而且违反的是我自己在文档里反复强调的那条纪律。

**根因：管道双向死锁。** `tools/verify_gui.ps1` 用
`ProcessStartInfo.RedirectStandardOutput = $true`，它建的是一根
**容量有限的匿名管道**（约 4 KB）。而脚本按"先 `WaitForExit`、再 `ReadToEnd`"
的顺序写——**父进程在子进程退出前不读**。上一轮输出少，没触发；
这一轮多加了十几条断言，输出超过管道容量，子进程阻塞在 write 上，
父进程在等它退出。

**讽刺的是**：头部注释里我自己写着"`ReadToEnd()` 排在 `WaitForExit()` 之前
会一直阻塞"（引 `01-反复犯的错.md` 错误六），却写出了**另一个方向的同一个坑**——
把读放到等待之后，同样会死锁，只是方向相反。

**规则补一条**：**子进程输出超过几 KB 时，不要用管道，用文件重定向。**
`build.ps1` 里的 `Get-ExeOutput` 有同样的隐患，一并改了。

## 反馈二：按钮偏大

**根因是 `wx.Window.FromDIP`。** 它在控件**尚未完成父级绑定**时退回 96。
实测同一个按钮：

| 运行方式 | `FromDIP(24)` | 实际高度 |
|---|---|---|
| 直接 `python src/main.py` | 24 | 24 逻辑像素（看不出问题） |
| 先 `SetProcessDpiAwareness(2)` 再跑 | → 42 | 42 物理像素 |

所以**这个缺陷只在 DPI 感知生效时才出现**——我平时的手工量测恰好绕过了它。
修法是主动问父窗口的 DPI，见 `widgets.dpi_of`（它必须 import wx，
所以放在 widgets 而不是 theme）。

**另一处让按钮"看起来更大"的原因**：按钮条给每个按钮加了
`wx.TOP | wx.BOTTOM` 各一个 `padding_gap`，**按钮高度因此翻倍**。
原实现纵向没有 padding，已改回。

## 反馈三：按钮排布被改了

原实现是"打开/切换排序在左，清空居中，顶置在最右"（两处 `AddStretchSpacer`）。
我第一版改成了"全部靠左"。**已按原样恢复。**

> 教训：**改动用户没要求的东西**，即使自认为更好看，也是引入风险。
> 排布属于"用户已经习惯的东西"，不在授权范围内。

## 反馈四：日期与时间不好区分

**我先试了"靠一个更醒目的分隔符"，但同一个分隔符在两种字号下观感差别很大**，
靠它不可靠。又试了"在单元格里换行分两行"——`DataViewListCtrl`
**会吞掉 `\n`**（`GetTextValue` 读得回来，但行高不变，实测仍是 23 像素）。

最终改成**两个独立列**：`访问日期` + `访问时间`。
中间有真正的列间距，任何字号、任何 DPI 下都分得清。
数据库里仍存整串，只在渲染时拆（`store.split_timestamp`）。

## 反馈五：置顶行的底色不对 —— 用户是对的，我给的颜色几乎看不出来

选中"底色"这一条时我先量了事实：

| | 底色 | 与白底的对比度 |
|---|---|---|
| 改前（`#FFF8DC` cornsilk） | | **1.065** |
| 改后（强调色向白推 0.86） | `#E1E8F8` | **1.228** |

**1.0 就是"完全看不出差别"**，1.065 实际上等于没有标记。这是我选色时
只凭"黄的代表固定"这个印象，没量过可辨度。

现在改成**从强调色算出来**（浅色向白推、深色向背景推），
换强调色时置顶底色跟着变。并且加了一条**以对比度为判据的测试**
（`test_pinned_row_is_visibly_different_from_the_background`，阈值 1.15），
不让它再悄悄退化。

**深色主题这一处返工了两次**：
① 朝纯黑推（`darken(accent, 0.78)`）得到 `#112B38`，亮度 0.0213
   比背景 `#202020` 的 0.0144 **还亮**——想变暗结果变亮了；
② 想压到背景之下也做不到，`#202020` 已接近纯黑，实测对比度上不去 1.11。
所以深色主题下置顶行是**提亮**的，与浅色主题同向，对比度 1.319。

## 关于深色主题：我理解错了用户的意思

用户说"深色主题未适配"。实测注册表 `AppsUseLightTheme = 1`，
**系统当前就是浅色**，所以程序显示浅色是正确行为。

但这条反馈仍然有价值——真正适配不了的是**原生控件**：列表表头、滚动条、
右键菜单、`MessageBox` 由系统绘制，`SetBackgroundColour` 对它们无效，
深色主题下它们仍是白底。这是 Win32 通用控件的限制，
已写进 `app.apply_window_theme` 的 docstring 而不是假装没有。

**用户选择"先不动，等我把系统切到深色再看看"。**

## 本轮的方法论收获

**我试了三种"证明界面好看/正确"的手段，三种都不可靠：**

| 手段 | 结果 |
|---|---|
| `ScreenDC.Blit` 抓屏 | 抓的是**屏幕**像素，窗口被挡住时抓到别人的画面 |
| `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` | DWM 合成窗口下**纵横交错的乱码** |
| `PrintWindow(hwnd, hdc, 0)` | 同样不可靠 |

**结论**：这个项目里，"界面观感"这一半**只能由人眼判断**。
能自动化的部分是"数值与可回读的属性"——列对齐、尺寸、对比度、行属性、

## 反馈 ②：「按钮四周圆角太小，看不出来；深色主题下四角还有没扣干净的白色像素」

**两个独立的缺陷。**

于是角上留了没扣干净的浅色像素。修法：先拿父窗口底色铺满整块客户区，

|---|---|---|

| 选中行 | **控件自绘**的系统高亮 | `SYS_COLOUR_HIGHLIGHT` = `(0,120,215)` |

### 缺陷一：`wx.Frame.SetWindowStyle` 根本不会置顶窗口

# 十、第四轮：用户说"你在越修越烂"——回归与修正

## 反馈 ①：「我明明规定了字体，为什么变更了列头的字体？现在它们的字体好难看」

**这是我引入的，而且原因很具体。** 原版 v1.1 的 `set_global_font`
（L700-714）是：

```python
self.SetFont(new_font)              # 设"本窗口默认字体"，向子控件传播
wx.Button.SetFont(self, new_font)
wx.StaticText.SetFont(self, new_font)
wx.TextCtrl.SetFont(self, new_font)
```

**关键：列表控件不在那三行里。** 原版的列表与列头用的是**系统默认字体**（9pt），
只有按钮/标签/输入框是 +1（10pt）。

我从第一版起就把 `self.SetFont(new_font)` 保留着，字体因此传播到**所有**子控件，
列头变成 10pt——与原版观感不同。

**修的时候还踩了一个顺序坑**：窗口级 `SetFont` 只传播给**当时已存在**的子控件。

| 尝试 | 结果 |
|---|---|
| 在 `InitUI` 之前 `set_global_font` | 列表还不存在，回退落空 → 10pt |
| 在 `InitUI` 之后设，但**先**回退列表**再** `SetFont(body)` | 传播把回退覆盖掉 → 10pt |
| **先 `SetFont(body)`，最后回退列表** | ✅ 列表 9pt、按钮 10pt |

而且自绘控件（派生自 `wx.Control`）**不吃 wx 的字体传播**，
要显式 `SetFont`（见 `_painted_widgets`）。地址栏输入框"比正文小一号"
也必须在正文确定**之后**再算，否则基准偏小（实测会算成 8pt 而不是 9pt）。

## 反馈 ②：「列头所有点击功能全部失效——你在越修越烂，请回头仔细阅读 1.1 版本的代码」

| 「圆角太大，要循序渐进」 | 4 → 12 跳了一整档。现在是 **8**（比例 1/3），比例改成具名常量，注释写明"再调以 ±2 为步长" |
| 「上下不需要间隔线」 | 原生 `LVS_EX_GRIDLINES` 是**横竖都画**，做不到只要竖线 → 改成自绘竖线 |
| 「黄色饱和度太低」 | 换成 `#FFE08A`。**注意：颜色是用户定的，不要再拿对比度计算去推翻它** |

关于置顶黄，用户那句总结值得单独记：

> "**不是你调色的问题，是此前不知道动错了哪些代码导致它失效。**"

我把它理解成"颜色选得不好"，量了对比度、换了色、又换成浅蓝——**在错误
的层面上改了四轮**。真正失效的是"行属性根本没被应用"。

**规矩**：用户说某个视觉元素不对时，**先确认它有没有被画出来**，再谈好不好看。

## 反馈 8：深色下表头白字浅底（第三次提出）

三条路都试过：

| 做法 | 结果 |
|---|---|
| `SetHeaderAttr()` | 返回 True，原生表头仍是 `#F0F0F0` |
| `SetWindowTheme` | 返回 True，表头像素仍是 `(255,255,255)` |
| `NM_CUSTOMDRAW` 子类化 | **能成，但没采用** |

第三条是 `SetWindowLongPtrW(GPWL_WNDPROC)` 级别的窗口过程替换，
**写错会直接崩掉进程**。本项目已经因为"改动过大"回归过两次，
不值得为一个表头冒这个风险。

最终用**纯 wx 的自绘表头**（`src/file_tracker/header.py`）把原生表头隐藏掉。
两个坑：`LVS_NOCOLUMNHEADER` 对已创建的列表无效（Windows 只在创建时看它）；
`Show()` 会把藏好的表头**重新显示**，而 `CallAfter` 在显示事件**之内**就跑完了
——所以用 `CallLater(60)` 排到队列尾部，并在 `on_show` 里也藏一次。

## 反馈 9（第 7 条）：「美学规范真的不能应用 roboc 那一种吗」

**能搬的已经搬完了**：系统取色、字体层级、圆角、强调色语义、双缓冲——
这些都在。剩下的（纵向节奏表、速率曲线、固定尺寸对话框、`WS_THICKFRAME` 结论）
是 Roboc 那个 C# 自绘进度窗专属的，与 wx 控件无关。

**用户随后选了四项**，本轮实现：

1. **一套真的配色方案** —— 中性色手工定，**不再从系统强调色推导**
   （原来拿高饱和强调色调亮当背景，用户改主题色整个界面就跟着变）。
   强调色只用于"程序推荐的那一个动作"。
2. **卡片分层** —— `background`（窗口底）与 `card`（内容区），
   表头与列表画在卡片上。**必须真的有一层容器**：
   直接给列表设底色看不出分层，因为列表会占满整块 sizer。
3. **统一间距网格** —— 全部间距改成 4 的倍数（4/8/12/16）。
4. **字体层级** —— 路径用正文 + 粗体（主信息），
   频次与时间用小一号 + 次要色。

## 顺带发现：我自己的编辑工具会剥掉 .ps1 的 BOM

用编辑工具改 `build.ps1` 之后，**BOM 没了**。Windows PowerShell 5.1
随即按 GBK 解码，中文注释变乱码，`}` 被吃掉，脚本报 34 个语法错误。

**这正是 `tools/add_bom.py` 那道门禁存在的理由**——它立刻抓到了。

# 十二、第六轮：双重顶栏，以及一个被渲染 bug 掩盖的错误判断

## 用户一句话点破的推理错误

我上一轮报告"原生表头已隐藏，只有一条顶栏"，依据是
**"深色主题下只数到一条顶栏"**。

用户指出：**"深色主题双重顶栏不可见，是因为此前你修不好的反色 bug。"**

**这一句把整个判断推翻了，而且他是对的。**

时间线还原：

| 阶段 | 浅色下看到的 | 深色下看到的 |
|---|---|---|
| 反色 bug 未修 | **两条顶栏**（用户第一张截图） | 一条（第二条白字浅底，看不见） |
| 反色 bug 修好 | 一条 | 一条 |

深色下"只有一条"从来不是"没有重复"的证据，而是**那条重复的顶栏
因为白字浅底而看不见**。我把渲染 bug 当成了功能正确。

> **规矩：拿"看不见"当"不存在"，等于把渲染 bug 当成功能正确。**
> 判据必须是**几何量**（占不占位置），不是"可不可见"。

## 真正的修法：`wx.LC_NO_HEADER`，不是 `LVS_NOCOLUMNHEADER`

之前的做法是"创建之后把原生表头藏起来"。**那条路从头到尾都不可靠**：
`Show()` 会把藏好的表头重新显示出来，所以我在三处补藏
（布局后、`CallLater`、`on_show`），而"补藏得逞没有"取决于事件循环时序——
一个靠时序碰运气的修法。

实测对比（同一次运行，只看**第一行的 y 坐标**）：

| 样式 | 第一行 y |
|---|---|
| `LC_REPORT` | **36** ← 表头占着位置 |
| `LC_REPORT \| LVS_NOCOLUMNHEADER`(0x4000) | **36** ← 被 wx 丢掉了，没用 |
| `LC_REPORT \| wx.LC_NO_HEADER`(0x800) | **0** ← 表头不占位置 |

两个关键发现：

1. **原生 `LVS_NOCOLUMNHEADER` 传进 `wx.ListCtrl` 会被 wx 丢掉**——
   原生 `GWL_STYLE` 里那一位根本没置起来（`0x4000` 不在
   `0x5201005d` 里）。wx 用的是自己的 `LC_NO_HEADER`(0x800)。
2. **表头窗口一直存在**（`SysHeader32` 会被创建），所以
   "窗口在不在""可不可见"都不是判据，**第一行的 y 坐标**才是。

那条 y=36 的空白就是用户看到的第二条顶栏。

## 判据也一并换掉了

验证脚本原来查的是"原生表头可不可见"——**那正是被渲染 bug 骗过的判据**。
现在查的是：

```python
frame.list_ctrl.GetItemRect(0).y <= 2      # 第一行贴近客户区顶部
```

以及一个显式的谓词 `app._header_reserves_space()`。
`_hide_native_header` 也从"藏掉一个窗口"退化成**保险**
（`LC_NO_HEADER` 已经生效时它什么都不做）。

## 本轮其余反馈

| 反馈 | 处理 |
|---|---|
| 「'频次'的三角被间隔线分割了」 | 竖线原本画在 `x + column_width - 1`，与标题末尾的排序三角撞上。新增 `header_separator_inset = 6`，竖线**往左挪** |
